# ENGIE最终留出与预测发布：A3交付

本轮完成事前冻结的2015最终评价、实际评分模型原字节服务交付，以及普通脚本与持久
发布的正常/故障对照。**共享收缩候选相对持久性等季度MAE改善2.985%，四个季度均
改善；五个最终模型已可在同一页面选择、回放和发布。**

入口：[历史预测](http://127.0.0.1:18000/#predict)，选择ENGIE的`2015-final`。
查看五模型对照，选择模型/时刻，运行六点预测；点击“发布本次预测”可获得数据库
读回的发布身份。处理中可刷新原记录，失败重试沿用请求身份，不延长截止时间。

这构成就业项目的新增实测成果。它不代表跨场站泛化、生产SLA、真实客户收益或全部
原定功能已经完成。开发期3%采用门仍未通过，默认保持持久性，候选可显式选择。

## 1. 事前冻结和独立评价

- 只使用2014训练，最后28天内层选型。标签加20分钟可得延迟后严格早于边界；
  内层最后训练起报为12月3日22:30，最终训练最后起报为12月31日22:30 UTC。
- Ridge在原三个alpha中选1；树仍为原400上限、ES40、seed42、两个CPU线程。
  L2与L1分别选每台/时距的树数；共享lambda从原五值网格选0.5。
- 内层选型60次与最终重拟合52次合计112次底层估计器拟合：Ridge16次、L2 48次、
  L1 48次，累计94.273秒；最终重拟合只在选择封存后进行。收缩复用L1，不新增训练。
  组件测试使用构造数据，其拟合不混入场站拟合数。2015不更新模型，不再调参。
- 最终五包先封存，再创建2015目标数组并评分；中断后的曝光标记禁止重新进入训练。
  [冻结协议](protocol.json)、[选择](selection.json)、[重拟合](refit.json)和
  [结果](result.json)保留独立身份与时间。此后只能复核，不重新宣称2015未见。

全年52,560个计划起报，51,200个输入合法，51,072个可完整评分（97.169%计划分母）。
五策略均实际输出全部51,200个合法输入。输入拒绝与没有未来标签分开：最后六个

## 2. 评分模型就是页面使用的模型

最终来源另设可信hash锚，旧2014信任锚和序列化类不变。先验证来源链，才反序列化，
在目标Linux CPU新进程禁止fit，全量重放后一次事务登记五包。原始模型字节就是
生成最终评分的字节；不在服务侧另训一个看似相同的模型。

- [独立复核](verification.json)：五策略完整重放最大差0；Ridge内层三alpha预测、
  lambda选择、train-only scaler、标签时间、所有指标/分组/分母复算通过。
  bootstrap另外用显式展开索引复算，不只调用同一个前缀和实现。
- [Linux CPU导入](cpu-import.json)：五包各51,200个合法起报，最大差4.55e-13kW；
  事前容差atol=1e-6、rtol=1e-8未放宽。[重复导入](cpu-reimport.json)返回同一身份。
- [HTTP与交付](http-delivery.json)：新五包和旧九包各首/中/末，共42组实际预测，
  直接输入与历史回放一致；旧Q4仍不开放2015实况。原Q1整行快照不变。
- [20项后端定向检查](focused-tests.xml)：构造拟合预算、边界/抽样、真实专属PG、
  迁移、导入、并发与发布、API轻量导入。没有重跑无关旧故障矩阵。
- [4个浏览器场景](browser-tests.json)：1440/390视口，六点实值/非空曲线/无溢出，
  发布并读回、选择隔离、可重试错误、pending原记录刷新。pending/错误响应是页面

- [重启读回](restart-readback.json)：API进程重启后15条场景记录、全部导入身份和

## 3. 交付对照真正证明了什么

两边使用相同Linux CPU环境、相同最终模型字节、相同输入与校验函数。五个起报按合法
索引等距选取，不按评分筛选；五类各5例，seed42打乱顺序，见[计划](delivery-plan.json)。
普通脚本保留正常输入校验、模型身份和内存去重，未故意删除这些基本保护。

| 场景 | 计划 | 普通脚本 | 持久发布服务 |
|---|---:|---|---|
| 正常 | 5 | 5份结果 | 5份有效发布 |
| 缺机组 | 5 | 全拒绝 | 全422拒绝、不登记发布 |
| 过期输入 | 5 | 全拒绝 | 全422拒绝、不登记发布 |
| 迟到结果 | 5 | 算完返回5份、无发布期限策略 | 真实算完，5条过期记录、0份有效发布 |
| 重复结果 | 5 | 内存去重后5份 | 生产finalizer再次消费相同真实结果，仍仅5份 |

按本次指定发布要求，25例判定全部符合预期：应拒绝15例中误接收0例，应接受10例中
误拒绝0例，重复有效发布0/5。脚本也正确处理了
输入和内存去重；新增价值是**可持久查询的身份、截止时间和原结果**。给脚本增加同等
持久事务合同也能实现这些能力，此结果不是相对成熟预测平台的优越性证明。

正常5例脚本推理合计0.197秒，服务HTTP全程0.325秒；时间边界不同，仅提供实际成本
观测，不计算虚构加速比、人工节省或队列耗时。迟到用声明的1ms加速故障预算，真实
推理完成后才拒绝，正常预算60秒；二者都不是生产SLA。

发布期限从PG接收登记开始，不从历史起报时间或HTTP到达时刻开始。事务先锁行，再
取`clock_timestamp()`，避免等锁后还使用事务开始时刻。相同key/payload重用身份，
更换payload或budget冲突；相同结果重投不改时间，冲突结果拒绝。幂等范围是一个
request_key/delivery_id，不是不同key的同一业务起报全局去重。

推理和终结整体由现有受限任务管理，取消等待方不跳过终结；测试验证真实PG仍发布。
硬杀进程不承诺自动重新计算：pending可按原ID查询并过期，结果不会静默借用旧预测。
`completed_at`是PG在取得终结锁后观察到完成的时间，不冒称纯推理结束时间。
