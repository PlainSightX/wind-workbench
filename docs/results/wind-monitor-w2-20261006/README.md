# 当前窗口的评分依据 W2

2026-10-06。针对已有延迟监测的普通报告/CLI改进，不新增模型或监测算法。
模型、实况模拟延迟、数据库表、评分公式和原12对/10%复核规则保持不变。

## 为什么改

旧CLI在累计已评分数量旁展示滚动MAE，却没有显示该MAE真正使用的窗口样本数。
已有API中的`rolling_pairs`与累计数分开，但普通展示容易让读者把累计数量当成评分依据。
这不是发现原数值计算错误，也不否定W1的预测/实况/恢复成果。

先新增两个针对性检查，旧产品代码下均失败：当前窗口没有完整缺口分区，CLI没有区分
累计数和滚动指标支持范围。原失败输出保存，没有以新检查失败重写历史验收结论。

采用已有PG账本的确定性分区，而不是新增ADWIN、在线训练或统计告警阈值。每个窗口起报
恰落入成对评分、待到达、到期缺失、无效输入或预测失败之一；单模型部分输出仍属失败。
完整性状态和相对误差复核分开。即使影子MAE没有超过复核线，缺测仍会明确显示。

## 普通路径与验证

纯规则实例中，累计28对不等于窗口24/36；其余12起报为4待到达、4缺测、2无效、2失败。
主用/影子MAE仍为1/1.05，原`within_margin`不变，另显式报告`incomplete`。
CLI显示两套计数和缺口，不仅在原始JSON中增加字段。

真实PG、原持久性/固定候选和普通HTTP检查使用24次起报、最近12次窗口。
人为延迟两个目标的一台机组实况，以可重复检查补齐行为；并非自然发生的遥测故障。

| 10分钟时距 | 累计成对数 | 窗口成对/已处理 | 窗口到期缺失 | 窗口完整性 |
| --- | ---: | ---: | ---: | --- |
| 补齐前 | 22 | 11/12 | 1 | incomplete |
| 补齐窗口外旧目标 | 23 | 11/12 | 1 | incomplete |
| 再补齐窗口内目标 | 24 | 12/12 | 0 | complete |

窗口外补齐后当前MAE/bias不变；窗口内补齐后重算指标。两个标签重投均返回同一报告，
更换应用和连接池后读回相同结果。既有真实TCP进程重启和独立CLI续跑检查也核对新窗口字段。
不把应用重建与真实进程重启混为同一证据。

## 边界与取舍

这轮改善的是使用者对监测结果的解释和追查能力，不是预测精度、统计显著性或效率增益。
`complete`只表示该已处理窗口的样本齐全；即使两模型同样差，也可能显示相对未超线。
测试中的补齐后复核变化由已有最小样本规则产生，不宣传为新算法发现漂移。

没有再跑一天历史回放、训练、参数选择、provider或性能实验。2015依然是已见历史数据。
普通18000运行栈未升级，公开v0.1.0没有这项维护增量；远端CI和旧镜像不证明新代码已部署。
原附件、首次失败及完整HTTP/检查结果私下保留，只把源码、测试和这份简明案例列入公开维护。
最终检查、源码锚与本轮临时资源退出由维护仓的工作包收据持有。

使用与字段含义见[延迟监测](../../engie-monitor.md)。本轮不继续加告警算法来扩大成果。
