# 公开发布候选 W2

日期：2026-10-03。目标是可读、可独立初始化、可核验的完整发布候选。
工程主体保持一份源码；本轮没有GitHub发布、远端CI、简历更新或新精度实验。

## 改动与可读性

- 纯回答校验移至 `assistant/validation.py`；AST复核确认校验函数语义未改。
- `workflow.py` 保留取证、图流程、provider、预算、一次修复和审计职责；
  `configuration.py` 明确环境优先及实际运行目录的密钥读取。
- 初始化在CPU容器执行，默认只配置；向量下载、索引与付费探针分别显式触发。
  API保持只读挂载，准备进程使用独立写入口及可写下载缓存。
- 原模型测试改为显式便携输入；默认软件组、原模型组、浏览器及provider组分开。
  新Ridge浏览器消费新实验回执，不再套用旧UUID或历史MAE。

这些改动没有替换预测默认、修改prompt v9.1/预算/校验合同，或提前完成预留结对行为。

## 真实问答与负结果

原两题及两个固定变体在当前实现上进行一批明确的HTTP确认，四份正文及引文独立复核通过：
Q1使用开发窗解释选择，正式结果只作事后核验；ENGIE说明开发改善1.80%、3%门未过、
默认持久性和正式改善2.985%，不以正式结果追认开发采用。

此前首次Q1在一次修复后因 `answer_number_unbound` 拒答，这个负结果保留。
在四题确认前另有两次显式诊断，其中第一次provider返回但私有捕获器UUID序列化失败，
不能宣称丢失的正文经过语义复核。诊断只证明可回答，不作为独立新题。
四题确认5次模型调用，加首次失败2次、诊断2次、新Ridge1次，共10次provider请求。
六次业务HTTP问答中一次拒答、五次通过；两个诊断为直接workflow请求。
这不是首次四题全过，也不是稳定性或开放问答准确率证明。

历史成功与当前请求均报告 `deepseek-flash`，没有模型身份变更证据。
语料、prompt、预算及校验保持一致；一次输出差异只支持模型回答存在波动。
新对象正文保留 `source_reported_unit`，不把未明确的代理数据单位改写成物理功率单位。

其他失败已修复并保留原始私有回执：Ridge请求漏填迭代参数及误判交付包数；
临时测试容器缺实际工作目录标签；准备卷合并仍只读；无home的运行用户下载缓存不可写。
API重启后私有辅助请求过早造成断连，确认没有审计/provider派发后，补健康检查再显式请求。
这些是执行/测试辅助层问题，不包装为模型优化收益。
