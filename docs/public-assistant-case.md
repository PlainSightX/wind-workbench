# 助手困难案例：有数值，不等于回答正确

结果助手的输入分成两类：用户明确选择的运行对象，以及只读的事实和文档。模型不能
改变对象范围，也不能执行 SQL、命令或网络访问。它只提出结构化回答，程序再检查事实
占位符、单位、引文和开发/正式评价所属阶段。

## 一个可复核的失败

用户问“Q1 推荐模型为什么没有采用 Transformer？”。最初回答用正式留出上 Transformer
落后于持久性的数字解释事前选择。数值本身有出处，但正式评价发生在选择以后，不能拿它
反推事前决定。另一个 ENGIE 回答报告了正式改善和未过采用门，却省略了所问的开发改善。
这两个精简原负例保留在[回归 fixture](../tests/fixtures/assistant/w1-negative-answers.json)，
真实错误是阶段推论和正文覆盖不足，不是 MAE 算错。

修复把开发依据、开发采用决定和正式结果分别绑定对象/来源，要求所问阶段在正文片段
实际出现对应事实与引文，然后由程序生成正文。不能只在事实列表附上正确数字来代替
回答。[stages.py](../src/power_forecast_service/assistant/stages.py) 负责阶段合同，
[validation.py](../src/power_forecast_service/assistant/validation.py) 负责渲染与绑定。
默认算法、原模型和预测结果没有因为解释修复而变化。

公开候选的同一 Q1 问题首次请求又返回了 `answer_number_unbound`。保存的
结果证明了两件事：模型调用完成过两次；最终草稿里有无法与绑定事实对应的数字，因而
程序拒绝把它当作成功回答。原始草稿没有被完整保留，不能据此断言模型当时具体写了
什么，也不能把原因归结为检索、模型或提示词中的某一个。

随后使用同一对象和冻结阶段来源的确认请求得到可验收回答，正文把开发选型、正式留出
和采用决定分开，并通过事实 ID 与原文片段绑定。这是一次可复现的处理路径，不是开放
问答准确率或稳定性证明。真实确认批次与首次负结果的范围见[W2记录](public-release-w2.md)。

## 维护者怎样定位下一次失败

当前实现对结构化输出 schema 失败只记录字段路径和 Pydantic 错误类型，例如
`answer:string_type`，不保存模型原文、密钥、URL 或完整提示。事实/引文校验失败仍记录
受限错误码和短诊断；可选草稿捕获失败不会跳过校验、repair 或必需审计，也不会增加模型
请求。维护者可以据此区分“输出格式不合格”和“内容证据不合格”，但仍需人工检查回答
语义。

事实列表正确也不能保证可见正文正确：正值占位符前添加负号，程序原先删除占位符
后再检查自由数字，漏掉了符号；补上检查后，同名标签又可遮挡负号，例如
`MAE=-ridge MAE：{{c0.ridge.mae}}`。页面全局删标签把后端通过的正文变成负12.5 kW。
现在服务器先规范占位符旁重复的同名标签，再检查符号/完整单位并生成正文；页面只
HTML转义展示服务器原正文，保留指标身份，不再删词或替换正文模型名字。
冗余同单位只在对应事实旁消费，不全局改其他文本。有限括号/Markdown的边界检查保留。
事实的真实负值正常渲染；纯文本页面的行首列表减号/加号规范为圆点，避免误读。
占位符已代表完整数值和单位，不额外附单位；英文说明先加句读，以区分未知单位后缀。
这种格式检查仍不证明任意自然语言的蕴含、单位换算或因果关系。格式错误沿既有一次
repair处理，第二次仍不合格就返回校验失败并完成必需审计，不展示错误草稿。

可运行 `python -m pytest tests/unit/assistant -q` 复核边界。阶段负例、正确 Q1/ENGIE
草稿、诊断捕获失败、schema 格式错误走各自检查；正确草稿通过注入 provider 的完整
工作流，并且审计被调用。这些是可重复软件检查，审计替身不冒充真实 PG，注入 provider
不冒充一次新的真实模型回答。

离线显示复核使用[检查入口](../tools/diagnostics/check_assistant_display.py)和
[浏览器消费者](../web/tests/assistant-offline.mjs)。准备项目原有前端依赖并按`web/build.mjs`
构建后，从项目根运行：

```text
python tools/diagnostics/check_assistant_display.py --output .local/assistant-display
```

检查走真实助手工作流的注入草稿，再用实际浏览器消费源码模块及生成的完整页面，核对
DOM正文与后端回答逐字一致、事实表和一次修复/拒绝。输出只写指定的私有目录，不随
公开树分发。Windows默认使用已安装Edge；其他系统需准备Playwright浏览器，亦可通过
`PLAYWRIGHT_CHANNEL`明确指定已有浏览器。44项观察是此固定回归的两个模式/两个视口，
不是44道未见模型题，也不证明普通服务或Linux浏览器已经在本轮实跑。

## 普通使用路径

用户准备一个已登记的 Q1 或 ENGIE 结果对象，提交问题并选择最多两个上下文。助手自主
读取结果事实、按固定策略检索文档、最多进行一次修复，然后返回带事实和引文的回答或
明确的证据不足/依赖错误。用户可以查看对象、来源和错误状态；预测与历史结果查询不
依赖助手成功。当前默认关键词检索，向量检索是显式准备后的可选路径。

## 覆盖范围

本地 `tests/unit/assistant` 覆盖事实符号/单位到正文的绑定、合法负值与列表标记、阶段身份、引文连续性、未知事实和伪造
引文拒绝、可选诊断失败、审计失败和结构化 schema 诊断。公开 CI 默认运行这些规则、真实
PostgreSQL/模型组件、端到端实验和浏览器检查，但不发送付费 provider 请求；真实问答
必须显式选择 provider 测试组。通过这些检查只证明对应边界，不等于开放问答质量保证。
